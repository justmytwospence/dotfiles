# Global Preferences

## Environment
- Dotfiles are managed by chezmoi from `~/dotfiles`; edit sources, never deployed `$HOME` copies. Before changing them, read `~/dotfiles/AGENTS.md` for project policy and synchronization, and `~/dotfiles/.agents/skills/chezmoi/SKILL.md` for general chezmoi guidance.
- npm, uv and pinned release binaries hold new releases for 7 days (`min-release-age=7` in ~/.npmrc; `npm view` ignores it and shows newer ones). The cooldown is for background and transitive updates. When I ask to install or upgrade a specific thing, take its exact requested (else newest) release right away through `~/dotfiles/docs/cooldown.md` (`cooldown-allow npm|uv <pkg>`, `linux_releases.py pin --tag`) and commit the allowance with the change; it lapses on its own, so that package's later updates wait again. Never exempt anything I did not ask for (dependencies, sweeping updates, tools you add yourself): for those, say when the release clears the cooldown. Pi (`@earendil-works/*`) and herdr are exempt.
- Pi suite components are developed in `~/Projects/pi-plugins/packages/<name>` and released as one Git package; test with `pi --no-extensions -e ~/Projects/pi-plugins`; publish first, then set the suite's Git spec in `~/dotfiles/home/private_dot_pi/private_agent/settings.managed.json` to the new commit and run `chezmoi apply`, whose converge script runs `pi update` (no manual `pi update`, no pin command). Do not develop in retained standalone pi repos. Other maintained plugins (opencode, herdr, anthropic-billing-guard) remain in their own `~/Projects/<name>` repos. Dotfiles only pins plugins. Never edit installed copies (~/.pi/agent/git, ~/.config/herdr/plugins, ~/.local/share/plugins). Follow ~/dotfiles/docs/plugins.md to test or publish.
- Skills install per project unless I ask for global: `npx skills add <repo> -s <skill> -a codex claude-code -y` in the repo root, then commit `.agents/skills`, `.claude/skills` and `skills-lock.json`. Global third-party skills are pinned, checksummed chezmoi externals in `~/dotfiles/.chezmoiexternal.toml.tmpl`; edit source and apply reviewed skill targets. Never use `npx skills add -g`, an `add` without `-a`, or `npx skills update`.
- On the NUC, a real browser for websites (no API, sign-ins, captchas, 2FA, account exports) is the `telebrowser` MCP server: one persistent profile per project, and you hand sign-ins to me with `browser_handoff`. Load the `telebrowser` skill before using it.
- To show me a page or an HTML file you made, or to drive a page I watch, use `terminal-browser` (load its skill): `open <url|file> --split right`, read with `action -- snapshot -i`, act on its `@e` refs, and finish with `action done`. On the NUC it can show pages but not drive them. Use the `chrome_devtools` MCP for headless debugging (console, network, performance) and `chrome_live` only for my logged-in Chrome.
- AgentBox boxes (hub on the NUC, boxes there or on Daytona): ~/dotfiles/docs/agentbox.md, including the `agentbox.yaml` task that applies these dotfiles in a box. Inside a box, `git` push/pull/fetch/clone go through the hub; do not add credentials there.
- Whenever a task touches a marimo notebook, load the global `marimo-style` skill alongside the project's `marimo-pair` skill.

## Git
- Conventional commits (feat:, fix:, refactor:, docs:, test:, chore:), one logical change each.
- Never force push to main/master.

## Worktrees
- Create one only when asked, always at `<project>/.worktrees/<branch>` (slashes as dashes), where `<project>` is the main checkout. Inside herdr use `herdr worktree create --cwd <project> --branch <branch> --path <project>/.worktrees/<branch>` (add `--no-focus` unless I asked to switch), which opens it as a grouped space; elsewhere `git worktree add <project>/.worktrees/<branch> -b <branch>`. Remove with `git worktree remove` (in herdr, `herdr worktree remove --workspace <id>`).
- For a user-requested feature or PR worktree in Herdr, create/open its dedicated space and start a persistent pi agent there before implementation. Treat this as a human-led handoff unless I explicitly request a headless worker. Give the agent the task, branch/base, current state, checks, and remaining work; verify it is running in that checkout and has received the handoff. A space with only a shell is not a finished handoff.
- Your original session stays where it started and coordinates; the worktree's agent owns its implementation, tests, commits, and PR updates. Do not keep editing that worktree from the parent session. Outside this interactive workflow, use absolute paths or `git -C` for an explicitly authorized headless worktree task.
- Every checkout lives in `<project>/.worktrees/` so every tool can find it. Claude Code's `--worktree`, `EnterWorktree` and `isolation: "worktree"`, pi's `/worktree`, pi-subagents' `worktree: true` and pi-herdr's `where: "worktree"` already land there, so they are fine to use. Never use a tool's own worktree location instead (Codex worktrees, which stay disabled; Paseo's `--new-workspace worktree`).
- Docker: never start, restart or recreate containers of a Compose project you did not start. A checkout that needs its own containers runs them as its own project (`docker compose -p <repo>-<branch>` plus an override outside the repo that renames containers and moves host ports), and joins shared services such as databases over their network instead of replacing them. Containers get AWS credentials by mounting `~/.aws`, never from exported or pasted keys.

## Delegation
- Default to headless subagents for delegated work that reports back to the main session, even if long, multi-step, or parallel. Do not create Herdr panes, tabs, or spaces for disposable report-back workers. Duration, complexity, and a hypothetical desire to watch are not reasons to start an interactive session.
- Start a persistent interactive agent only when the user requests one or the task is clearly a human-led handoff that the user will continue independently. A user-requested feature/PR worktree in Herdr is such a handoff, as specified above. Its ability to report back is coordination support, not a substitute for a headless subagent.
- For an interactive handoff sharing the current checkout and branch, use a tab in the existing Herdr space. Use a split only for deliberate side-by-side interaction or when requested. Tabs and splits share files; they are not isolated parallel editors. Keep focus unchanged unless asked to switch.
- An independent feature or PR may benefit from its own branch and checkout: use a new worktree's Herdr space only when the user requests a worktree or branch isolation; otherwise ask first. An already-open worktree space gets a tab there. Never create a new space or worktree merely because work is delegated, long, or parallel.

## Communication
- Be concise. Skip preambles and summaries unless asked.
- Deliver summaries and reports directly in the session. Do not create local report artifacts (such as summary or report files) unless explicitly requested.
- No emojis in code or documentation.
