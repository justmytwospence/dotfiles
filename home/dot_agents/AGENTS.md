# Global Preferences

## Environment
- Every repository I own or develop lives at `~/Projects/<repo>`, named after its GitHub repository (apps, MCP servers, plugins, forks). Clone new ones there, never into another directory under `~` (`~/mcp` was retired on 2026-10-21). The NUC's homelab is `~/Projects/homelab` too (it moved from `~/homelab` on 2026-10-29): it is the deploy checkout, and Docker Compose records its path as each stack's working directory, so run stack commands from that path. Checkouts inside another repo, such as homelab's `<stack>/app` submodules, are deploy pins, not development copies.
- Dotfiles are managed by chezmoi from `~/Projects/dotfiles`; edit sources, never deployed `$HOME` copies. Before changing them, read `~/Projects/dotfiles/AGENTS.md` for project policy and synchronization, and `~/Projects/dotfiles/.agents/skills/chezmoi/SKILL.md` for general chezmoi guidance.
- Package managers hold back releases younger than 7 days through their own config (npm, pnpm, yarn, bun, uv, pip on my machines; project repos carry their own), with Pi (`@earendil-works/*`), herdr, marimo and the packages I maintain exempt. The hold is only for background updates (versions chosen when nobody asked for one) and must never block or delay what we are doing. Install and upgrade normally; when the cooldown gets in the way of anything you are doing on purpose (a package, version or release you install, add, upgrade, deploy or test, a lockfile holding a recent version, a no-matching-version error, `npm view`/PyPI showing a newer release than you get), rerun that command as `fresh <command>`, which lifts it for that one command, and carry on. Never ask first, wait for a release to age, settle for an older version, or plan around the cooldown. Where the release must also install outside that command (a pin that dotfiles' converge installs, a project lock that CI resolves), add its exact-release allowance from `~/Projects/dotfiles/docs/cooldown.md` and commit it with the change, again without asking. Never remove the cooldown from a config itself.
- Pi suite components are developed in `~/Projects/pi-plugins/packages/<name>` (its AGENTS.md covers testing and rollout), never in retained standalone pi repos; other maintained plugins (pi-marimo, opencode, herdr) in their own `~/Projects/<name>` repos. Dotfiles only pins plugins; never edit installed copies (~/.pi/agent/git, ~/.config/herdr/plugins, ~/.local/share/plugins). Test and publish per `~/Projects/dotfiles/docs/plugins.md`.
- Skills install per project unless I ask for global: `npx skills add <repo> -s <skill> -a codex claude-code -y` in the repo root, then commit `.agents/skills`, `.claude/skills` and `skills-lock.json`. Global third-party skills are pinned, checksummed chezmoi externals in `~/Projects/dotfiles/home/.chezmoiexternal.toml.tmpl`; edit source and apply reviewed skill targets. Never use `npx skills add -g`, an `add` without `-a`, or `npx skills update`.
- On the NUC, a real browser for websites (no API, sign-ins, captchas, 2FA, account exports) is the `telebrowser` MCP server: one persistent profile per project, and you hand sign-ins to me with `browser_handoff`. Load the `telebrowser` skill before using it. Never use it (or any other browser automation) for marimo or MarimoHub: I open notebooks myself.
- To show me a page or an HTML file you made, or to drive a page I watch, use `terminal-browser` (load its skill): `open <url|file> --split right`, read with `action -- snapshot -i`, act on its `@e` refs, and finish with `action done`. On the NUC it can show pages but not drive them. Use the `chrome_devtools` MCP for headless debugging (console, network, performance) and `chrome_live` only for my logged-in Chrome.
- AgentBox: `~/Projects/dotfiles/docs/agentbox.md`. Inside a box, `git` goes through the hub; never add credentials there.
- Whenever a task touches a marimo notebook, load the global `marimo-style` skill alongside the project's `marimo-pair` skill.
- Whenever you send, reply to or draft email through the official Fastmail MCP, load the global `fastmail-mcp` skill first: replies must be sent from the address the thread was addressed to (my `*@spencerboucher.com` catch-all), never a default or Gmail sender.
- In a fork of an upstream project (remotes `origin` = upstream, `fork` = mine), load the global `fork-patch-stack` skill before changing, rebasing, deploying or auditing it.

## Git
- Conventional commits (feat:, fix:, refactor:, docs:, test:, chore:), one logical change each.
- Never force push to main/master.

## Worktrees
- Create one only when I ask for a worktree or branch isolation, always at `<project>/.worktrees/<branch>` (slashes as dashes), where `<project>` is the main checkout.
- Name branches with a short bare slug (`login-retry`, not `feature/login-retry` or `chore/login-retry`): type prefixes waste space in the herdr sidebar, status lines and paths. Use a prefix only when the repo requires one (CONTRIBUTING, branch protection, existing convention) or I ask.
- A worktree I ask for is where this conversation continues, not a reason to spawn another agent and coordinate it. In Pi inside Herdr, call the `herdr` tool with `action=spawn`, `where=worktree`, `fork=true`, the branch, and the next step as `task`, then end your turn: Herdr creates the checkout from the repo's default branch and this conversation continues there in the worktree's space as a child whose replies come back, while this session stays in the main checkout. In Claude Code, use `EnterWorktree`. Elsewhere, `herdr worktree create --cwd <project> --branch <branch> --path <project>/.worktrees/<branch>` (or `git worktree add <project>/.worktrees/<branch> -b <branch>` outside Herdr), and say plainly that this session cannot follow rather than silently starting a fresh agent. Start a separate persistent worktree agent only when I explicitly ask for another session, delegation, or a coordinator managing independent sessions; use a headless worker when requested.
- Removing a worktree once its branch has landed (in the repo's default branch, or a merged pull request) is Herdr's job: the worktree-reaper plugin removes landed, clean, idle worktrees with their space and branch, after a grace period (its `remove-landed` action does it at once). Do not remove them by hand unless I ask; outside Herdr, `git worktree remove`, then delete the branch.
- Every checkout lives in `<project>/.worktrees/` so every tool can find it. Claude Code's `--worktree`, `EnterWorktree` and `isolation: "worktree"`, pi-subagents' `worktree: true` and pi-herdr's `where: "worktree"` already land there, so they are fine to use. Never use a tool's own worktree location instead (Codex worktrees, which stay disabled; Paseo's `--new-workspace worktree`).
- Docker: never start, restart or recreate containers of a Compose project you did not start. A checkout that needs its own containers runs them as its own project (`docker compose -p <repo>-<branch>` plus an override outside the repo that renames containers and moves host ports), and joins shared services such as databases over their network instead of replacing them. Containers get AWS credentials by mounting `~/.aws`, never from exported or pasted keys.

## Delegation
- Delegated work that reports back goes to headless subagents, even if long, multi-step or parallel. Start a persistent interactive agent (Herdr tab, split or space) only when I ask for one or for a clear human-led handoff; a tab shares the checkout, a split is for deliberate side-by-side work, and a new worktree space needs my request.

## Communication
- Be concise. Skip preambles and summaries unless asked.
- Deliver summaries and reports directly in the session. Do not create local report artifacts (such as summary or report files) unless explicitly requested.
- No emojis in code or documentation.
