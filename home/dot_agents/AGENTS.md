# Global Preferences

## Environment
- Every repository I own or develop lives at `~/Projects/<repo>`, named after its GitHub repository (apps, MCP servers, plugins, forks). Clone new ones there, never into another directory under `~` (`~/mcp` was retired on 2026-10-21). The only exception is the NUC's `~/homelab` (the deploy checkout, whose path Docker Compose records as each stack's working directory). Checkouts inside another repo, such as homelab's `<stack>/app` submodules, are deploy pins, not development copies.
- Dotfiles are managed by chezmoi from `~/Projects/dotfiles`; edit sources, never deployed `$HOME` copies. Before changing them, read `~/Projects/dotfiles/AGENTS.md` for project policy and synchronization, and `~/Projects/dotfiles/.agents/skills/chezmoi/SKILL.md` for general chezmoi guidance.
- npm, pnpm, uv and pinned release binaries hold new releases for 7 days (`npm view` ignores this and shows newer ones); project repos carry their own cooldown config. When I ask to install or upgrade a specific thing, take that exact (else newest) release right away via `~/Projects/dotfiles/docs/cooldown.md` (`cooldown-allow` on my machines, the tool's native exact-release setting in a repo) and commit the allowance with the change. Never exempt anything I did not ask for (dependencies, sweeping updates, tools you add yourself): say when it clears the cooldown. Pi (`@earendil-works/*`), herdr and the packages I maintain are exempt.
- Pi suite components are developed in `~/Projects/pi-plugins/packages/<name>` (its AGENTS.md covers testing and rollout), never in retained standalone pi repos; other maintained plugins (pi-marimo, opencode, herdr, anthropic-billing-guard) in their own `~/Projects/<name>` repos. Dotfiles only pins plugins; never edit installed copies (~/.pi/agent/git, ~/.config/herdr/plugins, ~/.local/share/plugins). Test and publish per `~/Projects/dotfiles/docs/plugins.md`.
- Skills install per project unless I ask for global: `npx skills add <repo> -s <skill> -a codex claude-code -y` in the repo root, then commit `.agents/skills`, `.claude/skills` and `skills-lock.json`. Global third-party skills are pinned, checksummed chezmoi externals in `~/Projects/dotfiles/home/.chezmoiexternal.toml.tmpl`; edit source and apply reviewed skill targets. Never use `npx skills add -g`, an `add` without `-a`, or `npx skills update`.
- On the NUC, a real browser for websites (no API, sign-ins, captchas, 2FA, account exports) is the `telebrowser` MCP server: one persistent profile per project, and you hand sign-ins to me with `browser_handoff`. Load the `telebrowser` skill before using it. Never use it (or any other browser automation) for marimo or MarimoHub: I open notebooks myself.
- To show me a page or an HTML file you made, or to drive a page I watch, use `terminal-browser` (load its skill): `open <url|file> --split right`, read with `action -- snapshot -i`, act on its `@e` refs, and finish with `action done`. On the NUC it can show pages but not drive them. Use the `chrome_devtools` MCP for headless debugging (console, network, performance) and `chrome_live` only for my logged-in Chrome.
- AgentBox: `~/Projects/dotfiles/docs/agentbox.md`. Inside a box, `git` goes through the hub; never add credentials there.
- Whenever a task touches a marimo notebook, load the global `marimo-style` skill alongside the project's `marimo-pair` skill.
- Whenever you send, reply to or draft email through the official Fastmail MCP, load the global `fastmail-mcp` skill first: replies must be sent from the address the thread was addressed to (my `*@spencerboucher.com` catch-all), never a default or Gmail sender.
- In a fork of an upstream project (remotes `origin` = upstream, `fork` = mine), load the global `fork-patch-stack` skill before changing, rebasing, deploying or auditing it.

## Git
- Conventional commits (feat:, fix:, refactor:, docs:, test:, chore:), one logical change each.
- Never force push to main/master.

## Worktrees
- Create one only when asked, always at `<project>/.worktrees/<branch>` (slashes as dashes), where `<project>` is the main checkout. Inside herdr use `herdr worktree create --cwd <project> --branch <branch> --path <project>/.worktrees/<branch>` (add `--no-focus` unless I asked to switch), which opens it as a grouped space; elsewhere `git worktree add <project>/.worktrees/<branch> -b <branch>`. Remove with `git worktree remove` (in herdr, `herdr worktree remove --workspace <id>`).
- Name branches with a short bare slug (`login-retry`, not `feature/login-retry` or `chore/login-retry`): type prefixes waste space in the herdr sidebar, status lines and paths. Use a prefix only when the repo requires one (CONTRIBUTING, branch protection, existing convention) or I ask.
- A user-requested feature or PR worktree in Herdr is a human-led handoff (unless I ask for a headless worker): open its space and start a persistent pi agent there before implementation, give it the task, branch/base, state, checks and remaining work, and verify it received the handoff. That agent owns the worktree's implementation, tests, commits and PR updates; your session stays put, coordinates, and does not edit that worktree.
- Every checkout lives in `<project>/.worktrees/` so every tool can find it. Claude Code's `--worktree`, `EnterWorktree` and `isolation: "worktree"`, pi's `/worktree`, pi-subagents' `worktree: true` and pi-herdr's `where: "worktree"` already land there, so they are fine to use. Never use a tool's own worktree location instead (Codex worktrees, which stay disabled; Paseo's `--new-workspace worktree`).
- Docker: never start, restart or recreate containers of a Compose project you did not start. A checkout that needs its own containers runs them as its own project (`docker compose -p <repo>-<branch>` plus an override outside the repo that renames containers and moves host ports), and joins shared services such as databases over their network instead of replacing them. Containers get AWS credentials by mounting `~/.aws`, never from exported or pasted keys.

## Delegation
- Delegated work that reports back goes to headless subagents, even if long, multi-step or parallel. Start a persistent interactive agent (Herdr tab, split or space) only when I ask for one or for a clear human-led handoff; a tab shares the checkout, a split is for deliberate side-by-side work, and a new worktree space needs my request.

## Communication
- Be concise. Skip preambles and summaries unless asked.
- Deliver summaries and reports directly in the session. Do not create local report artifacts (such as summary or report files) unless explicitly requested.
- No emojis in code or documentation.
